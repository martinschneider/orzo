| H        | `MethodCallGenerator.generateChained()` L~632 | No generics tracking: a chained call on a generic method's return (e.g. `map.get(k).method()`, where `get` erases to `Object`) can't resolve `method` on the real (erased) type, so it falls through to the bare-name fallback and silently matches an unrelated same-named method on the enclosing class instead of raising an error. Root-caused via a minimal repro (`Map<Class,Gen> reg; reg.get(x.getClass()).generate(x)` inside a class that also declares a `generate(String)` method — the generated bytecode calls `this.generate(...)` instead of invoking on the map's value, which `VerifyError`s). Blocks self-compiling `StatementDelegator.java` (kept in `skiplist.txt`), whose `generate()` dispatches via `reg.get(stmt.getClass()).generate(...)`. Needs either generics-aware return-type tracking or restricting the bare-name fallback to true receiver-type-unknown cases.                                                                                                                                             |
| H        | `ForEachGenerator.isArrayIterable()`          | Only dispatches to the array for-each path when the iterable is a plain local variable (`stmt.iterable.tokens.size()==1 && instanceof Identifier` with a known `arrType`). A for-each over an array-*returning expression* (e.g. `for (Field f : clazz.getDeclaredFields())`) falls through to the iterator path instead, which assumes `java.lang.Iterable` and `VerifyError`s (`Type '[Ljava/lang/reflect/Field;' is not assignable to 'java/lang/Iterable'`). Needs `isArrayIterable`/`generateArray` reworked to infer array-ness from the expression's type (via `NumExprTypeDecider`) instead of requiring a bare variable, and to evaluate the iterable expression directly rather than assuming a `VariableInfo` lookup. Blocks self-compiling `ObjectUtils.java`, whose `hashCode()`/`equals()`/`toString()` all do `for (Field field : clazz.getDeclaredFields())`; kept in `skiplist.txt`.                                                                                                                                          |
| M        | `ForEachGenerator` (iterator path) / `UNBOX`  | `for (Integer n : list)` over a `List<Integer>` (boxed element type used as the loop variable's own type, i.e. no unboxing wanted) still goes through the CHECKCAST-only reference-element branch but then tries to `istore` the still-boxed `Integer` into an int-expecting slot — `VerifyError: Type 'java/lang/Integer' is not assignable to integer`. Minimal repro: `List<Integer> l = ...; for (Integer n : l) { use(n); }`. Needs `elemType`/loop-variable type inference to distinguish "boxed element kept boxed" from "primitive element, unbox it" consistently with how the loop variable itself is declared.                                                                                                                                                                                                                                                                                                                                                                                                                      |
| M        | `ArrayInitParser` / array-literal codegen     | `new String[] {...}` (or any reference-element-type array literal) emits `NEWARRAY` (primitives only) instead of `ANEWARRAY`, producing `VerifyError: Illegal newarray instruction`. Only primitive array literals (`new int[] {...}` etc.) work. Needs the array-literal codegen to pick `ANEWARRAY` + the element's JVM class when the element type isn't primitive.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| H        | `SwitchGenerator`                             | `switch` on an enum value compiles but is semantically broken: it does a direct reference comparison (`IF_ACMPEQ`/`IF_ICMPEQ` on the enum object itself) instead of calling `.ordinal()` (or `.name()`) first, so the comparison is against the wrong operand type and the JVM verifier rejects it (`VerifyError: Bad type on operand stack`, `Type 'Foo' is not assignable to integer`). Only `String` and integral switches work. Minimal repro: `enum Color {RED,GREEN,BLUE}` + `switch(c) { case RED: ... }`. Root-caused while investigating why `ScopeParser.java` — which does `switch ((Scopes) tokens.curr().val) { case PUBLIC: ... }` — can't come off `skiplist.txt`: self-compiling it produces a broken `ScopeParser.class` that corrupts parsing broadly (scope parsing runs for every class/method/field declaration), observed as ~180 unrelated `VerifyError`s across other self-compiled `*ParserTest`s. Needs `SwitchGenerator` to emit `.ordinal()` (or equivalent) before the comparison for enum-typed switch subjects. |
