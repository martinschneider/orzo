| M        | `MethodCallParser` / static-import resolution      | A bare (unqualified) call to a statically-imported **varargs** method (e.g. `import static ...FactoryHelper.list; ...; list(AccessFlag.ACC_PUBLIC, AccessFlag.ACC_STATIC)`) fails to resolve ("missing method declaration list[AccessFlag,AccessFlag,AccessFlag]"), even though `FactoryHelper.list(E... e)` exists. Reproduced self-compiling `EnumParser.java`, which calls `list(...)`/`id(...)` (both varargs on `FactoryHelper`) unqualified via static import. **Bigger than it first looked — not just a resolution gap.** `findMethodViaReflectionTyped()` requires an exact arity match (skips any candidate where `m.getParameterCount() != argTypes.size()`), so a varargs method called with any arg count other than its declared param count can never be found by reflection — this affects any reflective call, not just static-import ones. Fixing resolution alone isn't enough: the call-site argument-pushing loop in `MethodCallGenerator.generate()` (`for (int i = 0; i < types.size(); i++) { ...eval against method.args.get(i)... }`) assumes a 1:1 correspondence between call-site args and declared params, which breaks for varargs (3 call-site args against 1 declared `E... e` param — `method.args.get(1)` would throw). A real fix needs both: (1) varargs-aware matching in `findMethodViaReflectionTyped` (fixed params match normally; trailing args all compatible with the vararg component type), and (2) new codegen in the arg-pushing loop to build an array (`ANEWARRAY`/`NEWARRAY` + per-element store, same pattern as the now-fixed `DeclarationGenerator`/`ExpressionGenerator.createArray()`) from the trailing args instead of evaluating them 1:1. | H        | No generics tracking (type system)                 | Orzo has zero notion of generic type arguments: `DeclarationParser` sees `Map<K,V>`/`List<E>` in a declaration and just **discards** the `<...>` part (the "Skip generic type arguments" comment/loop), so a chained call on a generic method's return (e.g. `map.get(k).method()`, where `get` erases to `Object`) can never resolve `method` on the real (type-argument) type. Root-caused via a minimal repro (`Map<Class,Gen> reg; reg.get(x.getClass()).generate(x)` inside a class that also declares a `generate(String)` method — this used to silently call `this.generate(...)` instead of invoking on the map's value, producing a runtime `VerifyError` with no compile-time warning). **Partially addressed**: `MethodCallGenerator.generateChained()` had a "bare-name" fallback that, when the receiver-type-specific lookups failed, searched for a same-named method on the *enclosing* class as if it were an implicit-`this` call — but `generateChained` is only ever invoked for a genuine chain continuation (the receiver is always whatever the previous call returned, left on the stack), so this fallback was never semantically valid and always risked matching an unrelated method. Removed it (confirmic no existing test relied on it — full `mvn verify`/`-Pselfcompile` both stayed green). Chained calls on an erased generic return now fail loudly at compile time ("missing chained method ... on java.lang.Object") instead of silently miscompiling — a real safety improvement — but `StatementDelegator.java`, `DeclarationGenerator.java` (`arrInit.vals.get(0).size()`, `vals: List<List<Expression>>`), `ArrayInitParser.java` (same pattern), and `IncrementGenerator.java` (`ARITHMETIC_OPS.get(op).get(varInfo.type)`, `Map<Operators, Map<String,byte[]>>`) still don't *compile*, since none of them can resolve the chained call at all now. **A full fix needs real generic-argument tracking**, concretely: (1) capture the type argument(s) in `DeclarationParser`'s generic-skip loop instead of discarding them — e.g. a new `genericArgs: List<String>` field on `Type` (no constructor change needed, same pattern as the existing `type.arr` mutation); (2) thread it through to where the declaration becomes a `VariableInfo`/field entry (currently only `type.name`+`type.arr` survive into `Declaration`, so `Declaration` and the `MemberProcessor`/local-var paths that build `VariableInfo` would need to carry it too — a new mutable field on `VariableInfo`, not a constructor change, keeps this localized); (3) in `ExpressionGenerator`'s chain-walking loop, when the receiver is a field/variable with known `genericArgs` and the next call is `.get(...)` on a `Map`/`List`-shaped type, use the tracked value/element type argument as `receiverType` for `generateChained` instead of the erased runtime type.
